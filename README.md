# Customer Churn Prediction

This project predicts which telecom customers are likely to cancel their service. It compares four classical machine learning models and a neural network, and it explains which customer traits actually drive cancellations, not just how accurate the predictions are.

## The problem

A telecom company loses money every time a customer cancels. By the time someone calls to cancel, it is usually too late to change their mind. If the company could flag at risk customers early, it could step in first: offer a discount, fix a service issue, or just check in.

This project asks a simple question: using what we already know about a customer (their plan, how long they've been with the company, what they pay, which services they use), can we predict whether they are about to leave?

## Dataset

IBM's Telco Customer Churn dataset. It's public and widely used as a benchmark for this exact problem: 7,043 customers, 20 features.

| Category | Features |
| --- | --- |
| Demographics | Gender, senior citizen status, partner, dependents |
| Account | Tenure, contract type, billing method, monthly and total charges |
| Services | Phone, internet, security, backup, streaming, tech support |
| Target | Churn: yes (left) or no (stayed) |

About 26.5% of customers in the dataset churned, so the classes are imbalanced. That shapes a lot of the modeling decisions below.

## How the analysis works

The notebook walks through the pipeline step by step, with the reasoning written out in markdown before each block of code.

### 1. Exploring the data

Before building anything, I looked at what the data actually shows:

- Confirmed the 26.5% churn rate, which is why accuracy alone is a bad metric here (a model that just guesses "no churn" every time would still be right about 73% of the time).
- Checked tenure, monthly charges, and total charges against churn. All three show a clear split between customers who stay and customers who leave.
- Checked every categorical feature against churn. Contract type and internet service type turned out to be the strongest signals.
- Grouped customers into tenure cohorts (0 to 1 year, 1 to 2 years, and so on) to see how churn risk changes over a customer's lifetime.
- Checked correlations between numeric features. Tenure and total charges are correlated at 0.83, which makes sense since customers who stay longer pay more in total. Both were kept in the model since tree based models handle correlated features fine and logistic regression's regularization manages it too.

### 2. Cleaning the data

Only one real issue turned up: `TotalCharges` was stored as text instead of a number, because 11 brand new customers (tenure of 0) had a blank value instead of 0. Those were converted to numeric and filled with 0.

### 3. Preparing the data for modeling

- Dropped `customerID`. It's just an identifier with no predictive value.
- Label encoded binary fields like Yes/No and Male/Female.
- One hot encoded multi category fields like Contract, InternetService, and PaymentMethod.
- Scaled all features with StandardScaler. This matters for Logistic Regression and the neural network; tree based models don't need it but scaling doesn't hurt them either.
- Split the data 80/20 into train and test sets, stratified so both sets keep the same churn ratio.

### 4. Models trained

| Model | Why it's here |
| --- | --- |
| Logistic Regression | A simple, interpretable baseline. Good when the relationship between features and churn is roughly linear. |
| Decision Tree | Captures nonlinear patterns and produces rules a person can actually read. |
| Random Forest | An ensemble of trees that reduces overfitting through bagging. Reliable without much tuning. |
| Gradient Boosting | Builds trees one after another, each one correcting the last. Usually strong on tabular data like this. |
| Neural Network | A 3 hidden layer network with batch normalization, dropout, and early stopping, included mainly to see how it stacks up against the classical models. |

### 5. How the models were evaluated

Because the dataset is imbalanced, accuracy alone doesn't tell the full story, so five metrics were tracked for every model: accuracy, precision, recall, F1, and ROC-AUC.

For this specific business problem, recall matters most. Missing a customer who was about to churn is more costly than flagging a loyal customer by mistake. A false alarm just means an unnecessary discount offer; a missed churner is lost revenue.

## Results

| Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
| --- | --- | --- | --- | --- | --- |
| Logistic Regression | 0.740 | 0.507 | 0.786 | 0.616 | 0.841 |
| Decision Tree | 0.742 | 0.508 | 0.805 | 0.623 | 0.834 |
| Random Forest | 0.759 | 0.531 | 0.778 | 0.631 | 0.845 |
| Gradient Boosting | 0.807 | 0.671 | 0.535 | 0.595 | 0.846 |
| Neural Network | 0.744 | 0.511 | 0.797 | 0.623 | 0.836 |

(Numbers come straight from the notebook's own comparison table, so they'll match a fresh run with the same random seed.)

No single model wins across every metric, which is normal and worth noticing rather than glossing over:

- Gradient Boosting has the best accuracy and ROC-AUC, but its recall is the weakest of the five. It's cautious about predicting churn, so it misses more actual churners than the others.
- Random Forest has the best F1 score, the best balance between precision and recall.
- Decision Tree has the best recall. It catches the most churners, at the cost of more false alarms.

Given that recall matters most for this business problem, Decision Tree or Random Forest is the more defensible choice here, not Gradient Boosting, even though Gradient Boosting looks like the "winner" if you only check accuracy. That's the point of tracking five metrics instead of one.

## What the data shows

**Contract type is the single biggest driver of churn.** Month to month customers churn at 42.7%. Customers on two year contracts churn at 2.8%. If the business wants to cut churn, moving people onto longer contracts, through discounts or loyalty pricing, is the most direct lever available.

**New customers are the highest risk group.** Churn in the first year is 47.7%, and it drops steadily the longer someone stays, down to 6.6% for customers in their fifth or sixth year. Onboarding and early engagement matter more than almost anything else here.

**Fiber customers without security or support services churn heavily.** Customers with fiber internet but no online security and no tech support churn at 55%. They're paying more for a faster connection but getting no protection or help when something goes wrong, and it shows.

**Electronic check users are far more likely to leave.** Their churn rate is 45.3%, compared to roughly 15 to 17% for customers on automatic bank transfer or credit card. Moving people onto autopay looks like a low cost way to improve retention.

**Gender has no real effect.** 26.9% for female customers, 26.2% for male customers. Not worth building a targeted campaign around.

## What the neural network showed

The neural network performed reasonably well (0.836 ROC-AUC) but didn't beat the tree based ensembles, and that's actually the expected result, not a shortcoming of the implementation.

Deep learning tends to shine on unstructured data such as images, text, or audio, where it can learn its own feature representations. On tabular data like this, with about 7,000 rows and roughly 30 features after encoding, gradient boosting and random forests are usually competitive or better, and they're faster to train and easier to explain. The network's training curves showed clean convergence without overfitting, which is what dropout and early stopping are there for, but there was no reason to expect it to outperform the ensembles on data like this.

## Notes on the process

A couple of real bugs turned up while putting this together, and I think they're worth mentioning instead of hiding:

- The plots folder was being created in a later cell than the first plot that needed it, so the very first chart failed to save on a clean run. Fixed by creating the folder right after the imports, before anything tries to write to it.
- A feature importance summary used `.items()` on a pandas Series and then sliced it, which broke because `.items()` returns an iterator in current pandas, not something you can slice directly. Fixed by wrapping it in `list()` first.

Both are now fixed, and the notebook runs start to finish without errors.

## What I'd take from this project

- Look at the data before touching a model. The EDA step is what revealed that contract type and tenure were the dominant signals, and that shaped every decision after it.
- On an imbalanced dataset, accuracy is close to useless on its own. A model that always predicts "no churn" would still score 73% accuracy while being completely useless in practice.
- Scaling matters for some models and not others. Logistic Regression and the neural network need it; tree based models don't care either way. Scaling everything and letting the trees ignore it was simpler than maintaining two separate preprocessing paths.
- The best model depends on which metric the business actually cares about. Gradient Boosting wins on accuracy and ROC-AUC, but if recall is the priority, it's the worst choice of the five. Picking a "winner" requires knowing what you're optimizing for first.
- Deep learning isn't automatically the right tool. It performed fine here, but a simpler model did better and is cheaper to run and easier to explain. Knowing when not to reach for a neural network is as useful as knowing how to build one.
